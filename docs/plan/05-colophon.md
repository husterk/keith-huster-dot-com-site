# 05 · Colophon: "How this site was built"

Route: `/colophon` (linked from the footer as "How this site was built" and from the nav's Beyond-work area on wide screens). Same layout, type and colors as the homepage; a Markdown page with a short intro, a stack table, and a few paragraphs of decisions. It exists so a recruiter who wonders "did he really build this?" gets a specific, verifiable answer, including a link to the public repo.

Tone: matter-of-fact, first person, no marketing. Numbers where they exist (build time, page weight, Lighthouse scores), all measured after launch and updated when they change.

## Outline and draft copy

**Title:** How this site was built

**Intro (draft):** This site is a static page with one server endpoint, built and deployed the way I'd build a small production service: content and layout separated, everything validated in CI, secrets kept out of the repository, and the whole thing reproducible from a `git clone`. The source is public at github.com/husterk/keithhuster.com.

**Stack (table):**

| Layer | What | Why |
|---|---|---|
| Generator | Astro 5, static output | Zero JavaScript by default; content collections validate every YAML/Markdown file at build time |
| Content | YAML + Markdown in `src/content/` | Updating a role or a number is a one-line commit; the schema catches mistakes |
| Styling | Hand-written CSS with custom properties | The design is expressed as ~30 tokens; no framework needed |
| Illustrations | Inline SVG, generated from a small Python script during design | Crisp at any size, recolorable through one CSS variable, no image requests |
| Fonts | Barlow, Barlow Condensed, Spline Sans Mono, self-hosted | No third-party requests; preloaded to avoid layout shift |
| Hosting | Cloudflare Workers with static assets, custom domain | Static files served from the edge; one Worker handles the contact endpoint |
| Contact form | Worker endpoint + Turnstile + Resend + rate limiting | No third-party form service; spam handled at the edge |
| Analytics | Cloudflare Web Analytics | Cookieless, no consent banner |
| CI/CD | GitHub Actions: type/schema checks, Playwright, axe, Lighthouse CI; preview deploy per PR; deploy on merge | Nothing reaches production that CI didn't build and test |
| Secrets | 1Password service account; Worker secrets synced on deploy | The repository can be public; GitHub holds a single token |

**Decisions worth a paragraph each (drafts):**

- *Why not React.* There is one interactive element on the page (the mobile menu) and one form. A framework runtime would be the largest asset on the site and would buy nothing. Astro leaves the door open for an island if that changes.
- *Why the illustrations are code.* The six scenes and the bikepacker are SVG generated by a script, so the whole route from Banff to Antelope Wells weighs less than one photograph, scales to any screen, and picks up the accent color from CSS. On phones each scene re-frames around the rider instead of shrinking.
- *How content updates work.* Edit a YAML file, open a pull request, get a preview URL, merge. If a field is missing or a date is malformed, the build fails with a message pointing at the line.
- *What the numbers say.* Page weight, requests, build time, Lighthouse scores (filled in after launch; keep to one sentence each).
- *What I'd change at scale.* Honest note: for a multi-author site I'd add a CMS; for a product I'd add an image pipeline and a real design system. For one person and one page, this is the right amount of machinery.
